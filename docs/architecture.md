# 付箋データの同期アーキテクチャ

## 前提

- 拡張機能はほぼ全ページで動作するため、`content script` が付箋ルールを表示するたびに
  PocketBase へ問い合わせるのは避ける（ネットワーク遅延・オフライン耐性・結合度の観点）。
- 代わりに、DB のデータを `browser.storage.local` にミラーし、`content script` は
  ローカルの読み取りのみで動作させる。

## 原則: DB is source of truth / local storage は読み取り専用ミラー

```
[popup: 新規付箋作成]
        │
        ▼ 書き込みは常にDBへ直接
   [PocketBase]
        │
        ▼ pull（一方向の同期。local -> DB の書き込み経路は存在しない）
[browser.storage.local]
        │
        ▼ read-only
[content script: URL判定 & 表示]
```

- 書き込み経路は popup → PocketBase の一本のみ。
- local storage への書き込みは同期処理（background script）のみが行う。
- local storage → DB という経路は存在しない。これにより競合解決やマージロジックが不要になる。

## 同期方式: リアルタイム購読 + 定期フォールバック

| 経路 | 方式 | 役割 |
|---|---|---|
| リアルタイム | PocketBase SDK の `subscribe` イベントを都度 local storage に反映 | 通常時の即時差分同期 |
| フォールバック | 起動時 + 一定 interval で **全件取得して丸ごと上書き** | 接続断・イベント欠落・拡張機能再起動からの復旧 |

### なぜ timestamp ベースの差分ポーリングを採用しないか

`updated` フィールドを使った `filter=(updated>X)` は作成・更新の差分取得はできるが、
**削除されたレコードは検知できない**（存在しないレコードは検索結果に出てこないため）。

これに対処するにはソフトデリート方式（`deleted` フラグを立てて論理削除）などの追加ロジックが
必要になり、複雑さが増す。よって以下の役割分担とする。

- **差分はリアルタイム購読イベントでもらう。**
  各イベントは `action`（create/update/delete）と `record` を含み、それ自体が1レコード分の
  差分になる。ローカル側の処理は単純:
  - `create` / `update` → `storage[record.id] = record` で上書き
  - `delete` → `storage` から該当エントリを削除
- **フォールバック同期は差分計算をせず全件取得で正確性を担保する。**
  個人用途でレコード数が少ない前提なら全件取得のコストは無視でき、削除の見落としも起きない。

## 注意点

- リアルタイム購読は SSE（EventSource）による長時間接続のため、再接続・トークン失効への
  対応が必要。ただしフォールバック同期があるので、接続断に神経質になる必要はない
  （多少ズレても次のフォールバック同期で直る）。
- MV3 ビルドを見据える場合、service worker が非アクティブ化されると接続が切れるため、
  再購読ロジックが別途必要になる。
